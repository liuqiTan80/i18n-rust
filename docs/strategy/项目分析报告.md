# zrRust（rzc）项目分析与合理化建议

> 分析日期：2026-09-04 · 版本：v0.7.0 · 分析范围：全仓库（Rust 工作区、CI、教程、扩展、仓库卫生）

---

## 一、项目总体评价

**项目定位清晰、工程质量高于绝大多数同规模个人项目。** rzc 是一个多语言 Rust 方言编译器：母语源码 → 词法转译 → 标准 Rust → 官方工具链编译，再把诊断翻译回母语并附教学提示。架构上"引擎语言无关 + 语言包数据驱动"的设计（新增语言零代码改动）是本项目最大的技术亮点。

| 维度 | 数据 |
|---|---|
| Rust 工作区 | 3 crates（engine / cli / lsp），35 个 .rs 文件，约 2.55 万行 |
| 语言包 | 10 种自然语言，编译期嵌入 |
| 测试 | 424 个测试函数 / 30 个测试模块，含 proptest 模糊测试与 LSP e2e |
| CI | 7 大任务门禁（详见下文） |
| 配套 | 25 章中文教程（CI 逐块验证可编译）、VS Code 扩展、离线打包脚本 |

### 做得好的地方（值得保持）

1. **CI 门禁体系非常完整**：fmt + clippy `-D warnings`（宣称零警告）、MSRV 1.88 门禁、debug + release 双模式测试、llvm-cov 行覆盖率 ≥70% 门禁、criterion 基准回归对比、三平台构建、教程代码块逐块编译验证、映射质量门禁、RustSec 审计。这套体系达到成熟开源项目水准。
2. **代码注释与文档质量高**：关键设计决策都有说明（如 `column_map.rs` 中明确区分"CLI 用字符列 vs LSP 用 UTF-16 列，不可混用"——这是极易踩的坑，文档化非常专业）。
3. **安全意识到位**：ZIP 解压正确实现了 zip-slip 防护（拒绝绝对路径与 `..` 段）；工具链下载有 SHA-256 校验；AI 调用走环境变量（`DEEPSEEK_API_KEY`），无硬编码密钥；依赖选型避开 OpenSSL（ureq + rustls）。
4. **测试纪律好**：本次工作区中未提交的 bug 修复（教学提示只输出首条的回归）就附带了完整的回归测试，修 bug 带测试的习惯已内化。
5. **依赖管理克制**：engine 仅 5 个运行时依赖，选型（rustc_lexer、encoding_rs）合理。

## 二、发现的问题与合理化建议

### 1. 仓库卫生（优先级：高，改动成本低）

根目录有多处开发过程遗留文件已被提交：

| 文件 | 现状 | 建议 |
|---|---|---|
| `test.rs` / `test.zh` / `error_test.zh` | 手工调试用例 | 删除，或移入 `examples/` 作为文档化示例 |
| `conversation.md` / `i18n-rust.md` | 开发笔记/设计稿 | 移入 `docs/dev/` 或删除 |
| `verify_blocks.sh` | 早期验证脚本，已被 `tools/verify-tutorials.py` 取代 | 确认后删除 |
| `.zh-demo/`（8.9 MB 演示项目） | 已提交进仓库 | 明确其用途；若只是演示，缩减体积或移入独立仓库 |
| `crates/cli/.rz/`（未跟踪） | 运行时产物 | 在 `.gitignore` 中加一行 `.rz/` |

### 2. 未提交的工作区改动（优先级：高）

当前工作区有 5 个文件被修改、1 个新文件未跟踪：

- `crates/engine/src/column_map.rs`（新模块，**已被 `lib.rs` 引用**）
- `crates/engine/src/diagnostic.rs`：修复"教学提示仅输出首条"的回归 + 配套测试
- `crates/cli/src/main.rs`、`cache.rs`、`mapping_manager.rs`、`lib.rs`：配套改动

这意味着**新克隆本仓库可编译，但当前开发机的工作区处于半成品状态**。这些改动质量不错、测试齐全，建议尽快整理提交，避免与后续开发混淆或意外丢失。

### 3. Cargo 工作区配置可优化（优先级：中）

根 `Cargo.toml` 目前只有 members、resolver 和 rust-version，建议补充三块：

```toml
[workspace.dependencies]
# toml / serde / serde_json / anyhow / tempfile / rustc_lexer
# 目前在 2-3 个 crate 中重复声明同版本，统一后避免版本漂移
toml = "0.8"
serde = { version = "1", features = ["derive"] }
# ...

[profile.release]
lto = "thin"          # 发布包体积与运行性能
strip = true          # 发行版二进制显著减小（对离线分发包尤其有价值）
codegen-units = 1

[workspace.lints.clippy]
# 把 CI 中的 clippy 规则显式落库，本地与 CI 行为一致
```

三个 crate 的元数据也有小问题：`repository` 字段有的指向 GitCode（`gitcode.com/tan80/i18n-rust`），`homepage`/CI 徽章指向 GitHub（`liuqiTan80/i18n-rust`）。若双平台镜像是有意为之，建议在 README 顶部说明镜像关系；否则统一。

### 4. 大文件拆分（优先级：中）

按行数排序的热点文件：

| 文件 | 行数 | 建议 |
|---|---|---|
| `cli/src/mapping_gen.rs` | 2475 | 拆为 provider（AI 调用）/ 提取 / 翻译三个子模块 |
| `lsp/src/response_map.rs` | 2447 | 按 LSP 请求类型分组拆分 |
| `cli/src/main.rs` | 2202（51 个函数） | clap derive 已按子命令结构化，把每个子命令的 handler 移到独立文件 |
| `lsp/src/server.rs` | 2130 | 分离请求处理 / 翻译调度 / 文档同步 |
| `engine/src/diagnostic.rs` | 1822 | 诊断模型 / 翻译逻辑 / 文本渲染三分 |

非紧急，但 mapping_gen 已承载 AI 提供商扩展（DeepSeek/Anthropic/Gemini），继续膨胀会加速。

### 5. 测试布局补强（优先级：中）

- `crates/cli` **没有任何集成测试目录**（engine 有 fuzz，lsp 有 e2e）。CLI 是用户直接接触的面，建议用 `assert_cmd` + `predicates` 增加子命令级集成测试（`rzc init/run/check/eject` 的端到端行为）。
- engine 非测试代码中有约 57 处 `unwrap()`，作为发布到 crates.io 的库 crate，建议逐步替换为错误传播；LSP 主循环的 8 处 unwrap 属常见做法，加注释说明 panic 恢复策略即可。
- 覆盖率门禁现为 70%，可在 CLI 集成测试补齐后逐步提到 80%。

### 6. 11 份 README 翻译的维护成本（优先级：低）

`README.{en,ja,ru,es,fr,de,ko,ar,pt,hi}.md` 共 10 份翻译。人工同步 11 份文档几乎必然滞后，建议二选一：

1. 在非中英 README 顶部加注"内容可能滞后于中文版，以 README.md 为准"；
2. 或在 CI 中加一个轻量检查：中文版结构性章节（标题数）与其他语言差异过大时警告。

教程翻译同理（README 已声明欢迎社区翻译，风险可控）。

### 7. 其他小建议

- **本地 target 目录已达 11 GB**：定期 `cargo clean` 或使用 `cargo-sweep`；CI 已有 Swatinem/rust-cache，本地无需保留全部历史产物。
- **AI 提供商配置**：目前 DeepSeek 走环境变量 + 可选 BASE_URL，建议统一为一个 provider 抽象（规划中已有），并把 base_url/model 也纳入 `--provider` 参数体系，减少环境变量数量。
- **发布流程**：crates.io 发布路径依赖（path → version 转换）已在 Cargo.toml 注释中说明，建议把 `cargo publish` 顺序（先 engine 后 cli/lsp）写进 release-offline 脚本或 CI release workflow，防呆。

## 三、总结

| 类别 | 结论 |
|---|---|
| 架构设计 | ★★★★★ 语言包数据驱动、引擎语言无关，是项目的核心竞争力 |
| 工程实践 | ★★★★★ CI 门禁体系完整度罕见（MSRV/覆盖率/基准/fuzz/教程验证） |
| 代码质量 | ★★★★☆ 注释与测试纪律好；大文件需拆分、engine 需去 unwrap |
| 仓库卫生 | ★★★☆☆ 根目录遗留文件、未提交改动、.gitignore 缺项 |
| 可维护性 | ★★★★☆ 大文件与 11 份 README 是主要长期负担 |

**最值得立即做的三件事**：
1. 提交当前工作区的修复（教学提示回归 + column_map 新模块）；
2. 清理根目录遗留文件，补 `.gitignore`（`.rz/`）；
3. 补充 `[workspace.dependencies]` 与 `[profile.release]`（strip + thin LTO，直接减小离线分发包体积）。
