## 一、结论先行

从即日起：

1. **`main` 只能通过 PR 合并**，任何直接推送都会被分支保护规则拒绝；
2. **`main` 只接受 `zh` 分支执行 `rzc eject` 生成的代码**，不能把 `zh` 直接 merge 进 `main`；
3. **`zh` 是唯一日常开发分支**，功能、修复、文档、语言包、CI 改动都先在 `zh` 完成并验证；
4. 发布由发布负责人生成 `release/eject-<版本>` 候选分支，走 PR + 评审 + 必需检查后合并。

请所有成员在继续提交前阅读
[《分支保护与发布流程》](分支保护与发布流程.md)，并回复「已读 + 姓名」。

## 二、分支角色

| 分支 | 用途 | 提交方式 |
|---|---|---|
| `main` | 发布树（标准 Rust，`.rs` 入库） | 仅 PR；禁止直接推送 / 强推 / 删除 |
| `zh` | 日常开发（只保留 `.zh` 方言源） | 直接推送；禁止强推 / 删除 |
| `release/eject-<版本>` | 发布候选（由 zh eject 生成） | 发布负责人推送，PR 合并后删除 |
| `v<版本>` | 发布标签 | 仅发布负责人；禁止删除 / 移动 |

## 三、`main` 的保护规则（已配置）

- 禁止直接推送、强制推送、删除；
- 必须通过 PR，至少 1 人批准 + CODEOWNERS 批准；
- 必须通过状态检查：`test`、`windows-gates`、`msrv`、`eject-verify`；
- 分支必须是最新的；只允许线性历史（Squash / Rebase，禁止 merge commit）；
- `eject-verify` 会比对候选树与 `origin/zh` 的 eject 产物，**不一致直接红**。

## 四、日常开发怎么做

```bash
git switch zh
git pull --ff-only

# 1) 只改 .zh / 语言包 / 文档 / 工具
# 2) 本地门禁
make zh-build ARGS='test --workspace --locked'
make zh-artifacts
make zh-ascii

# 3) 提交并推送
git add -A && git commit -m "feat(engine): …"
git push github zh
```

- 不要直接在 `zh` 上 `cargo build`（源码树只有 `.zh`，cargo 会报无构建目标）；
- 不要在其他分支长期开发；临时分支只用于发布候选，合并后删除；
- 推送 `zh` 后 `zh-gates` 必须绿，红了立即修。

## 五、发布怎么做（发布负责人）

```bash
# 0) 确认 zh 干净、版本号已统一
git switch zh && git pull --ff-only

# 1) 生成发布候选（自动 eject + 格式化 + 提交）
scripts/prepare-eject-branch.sh 0.9.1

# 2) 推送并开 PR
git push -u github release/eject-0.9.1
# GitHub: base=main, compare=release/eject-0.9.1
# PR 描述写：zh@<sha>、版本号、变更摘要、已跑门禁

# 3) 等 eject-verify / test / windows-gates / msrv 全绿
# 4) CODEOWNERS 批准 → Squash merge
# 5) 打 tag 并镜像
git switch main && git pull --ff-only
git tag -a v0.9.1 -m "rzc 0.9.1" && git push github v0.9.1
scripts/mirror.sh v0.9.1
```

## 六、明确禁止

- ❌ `git push github main`（会被拒绝）
- ❌ `git push --force` 到 `main` 或 `zh`
- ❌ 把 `zh` 直接 merge / rebase 到 `main`
- ❌ 手工修改 `main` 上的 `.rs` 后提交
- ❌ 绕过 PR 用管理员权限强推
- ❌ 删除或移动已发布的 `v*` 标签

## 七、常见问题

**Q：我直接 push main 被拒了怎么办？**
A：这是预期行为。把改动放到 `zh` 分支，按第五节流程发布。

**Q：PR 的 `eject-verify` 红了？**
A：说明候选树不是当前 `zh` 的 eject 产物。回 `zh` 修复并 push，然后重新运行
`scripts/prepare-eject-branch.sh <版本>`，不要手工改候选分支。

**Q：为什么不能把 zh 直接 merge 到 main？**
A：`main` 是标准 Rust 发布树，`zh` 是方言源；直接合并会把 `.zh` 带进 `main`，
且缺少 `.rs` 产物。必须由 `rzc eject` 生成候选树。

**Q：紧急修复也要走 PR 吗？**
A：是。紧急修复同样先在 `zh` 完成并验证，再 eject 成候选分支；规则集没有配置
管理员 bypass，任何直接推送都会被拦截。
