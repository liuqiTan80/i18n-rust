# 中文自举分支导读（exp/zh-selfhost）

> **定位**：本分支是「用中文写编译器自身」的**学习与参考**实现——把 zrRust 全库
> Rust 源码翻转成 `.zh` 方言源真相并保证与生产产物逐字节一致。产品主线仍以英文
> 源码为主，本分支不合回主干。
>
> 想理解方言转换框架本身，先读 [方言编程框架生成蓝图](./dialect-framework-blueprint.md)；
> 想为新语言包做同样的自举，本文的翻转工作流与保留类判据可以直接复用。

## 1. 源真相模型

```
crates/**.zh  ──(tools/zh-selfhost/regen.sh: stage 拷贝 → rzc eject → rustfmt)──▶  同名 .rs 产物
```

- `.zh` 是唯一可编辑真相；`.rs` 是生成物，由 `make gate` 中的 `regen --check`
  做**逐字节一致**核验，任何漂移即门禁失败。
- eject 还原依据 `crates/engine/lang-packs/zh/*.toml` 词条表 +
  `crates/**/映射源.zh` 运行时词表，因此**改名必须正反两向都成立**：
  中文标识符 → 还原英文 → 与旧产物一致（或直接以中文标识符编译，两代产物同源）。
- **覆盖面不变式**：`regen --check` 除逐字节一致外，还反向断言
  `crates/**/*.rs` 每一个都有同目录同名 `.zh`——因 regen 只遍历 `.zh` 生成，
  若有人塞入无 `.zh` 配对的英文 `.rs`（绕过自举），`--check` 本就看不见它，
  此断言专门拦截这类孤儿，机器担保“全部模块源真相反转”的声明。
  - **无需排除白名单**：`build.rs`、cli `main.rs`、`benches/*.rs`、`tests/*.rs` 这些
    按 cargo 约定保留英文名的产物，**源真相层仍是中文**（`build.zh`→eject→`build.rs`）——
    约定只钉在 eject 的**产物名**上，不豁免 `.zh` 配对。故断言扫它们全部命中、
    零误报；切勿因“这些本该是英文”而给断言加排除项，那会在真孤儿 `.rs` 上重撕缺口。
- 用户可见/对外契约用显式手段钉死英文：clap `#[command(name)]`/`#[arg(long)]`
  保住 CLI；build.rs 生成契约（内置文件清单/界面表路由/引擎源码指纹）双侧同步；
  serde/LSP JSON 协议键原样透传。

## 2. 终审五线总览

前四线针对 `.zh` **源码**（逐面消除英文残留），第五线针对**文档**（改名后指向
代码的引用会滞后）；五线全部收口后分支才算自洽。每线的验收都是：
`扫描器定位 → 词条/存在性核验 → regen → build → fmt → test → make gate` 逐字节一致。

其中**源真相逐字节一致（`regen --check`）、覆盖面断言、`.zh-demo` 往返校验**这三道
不仅本地 `make gate` 跑，也已作为独立步进 **CI `test` job**（将 CI 自建 rzc 注入 PATH
后调用；`--check` 只读不覆写产物，故用自建 rzc 安全且更严格），对所有贡献者强制。

| 线 | 内容 | 例子 |
|---|---|---|
| 标识符面 | 模块/类型/函数/字段/局部变量/循环/参数/闭包参数 | `TranslationCache → 翻译缓存`、`\|k, v\| → \|键名项, 值项\|` |
| 关键字面 | 有中文词条的关键字 | `continue→继续`、`break→中断`、守卫 `if→如果`、`&mut→&可变`、`fn drop→函数 丢弃`、`ref→引用绑定`、`true/false→真/假` |
| 黏连混合面 | 中英拼接标识符 | `原始uri→原始资源定位`、`zh_len→中文长度` |
| 属性位 | derive 与属性名 | `#[derive(Debug, Clone)] → #[派生(调试, 克隆)]`、`#[cfg(test)] → #[配置(测试)]` |
| 文档面 | 导航表/crate README/演示注释里指向代码的失效英文路径与符号（详见第 7 节） | `ui.rs→本地化.rs`、`mapping_manager::MappingManager→映射管理::映射管理器` |

## 3. 保留类白名单（为什么这些保持英文）

1. **外部 ABI 与 std/第三方路径段**：`Vec`/`HashMap`/`lsp_server::Request` 类型名、
   `std::thread::spawn`、rustc_lexer 字段 `suffix_start`——词典不管或还原即断。
2. **协议与序列化契约**：serde/LSP JSON 协议键（`"uri"`、`"id"`、`"method"`）、
   `#[serde(rename = "…")]`、clap `#[arg]`/`#[command]`、`#[allow]`（无中文词条的属性名）。
3. **字符串夹具与生成串契约**：测试里的英文 Rust 样本、提示词、
   模块路径.zh 生成的 `#[path = …]` 输出——它们是数据不是代码。
4. **字面名/专名混排**：`src目录`、`Cargo.lock`、`cargo路径`、`rustc就绪`、`JSON序列化`、
   `fnv1a混列`——名字本身就是英文专名，中文化反而丢义。
5. **生命周期与转义**：`'static`/`'a`、`'\u{FEFF}'`、`b'0'..=b'9'`。
6. **CLI 本地化兜底文案**：`crates/cli` 里 clap derive 的 `///` 帮助注释与顶层
   `#[command(about = …)]` 兜底**故意留英文**，运行时被 `界面.取文(键)` 按界面语言
   逐条覆盖（`main.zh` 有数十处此调用）——这是多语编译器的中立兜底，非全中文漏网。
   源码里紧靠的注释 `// 兜底文案（本地化 clap 会按界面语言覆盖）；用英文避免硬编码中文`
   就是这个意图。判据：强制重编后 `rzc --help` 实际输出已中文、无英文泄漏；**勿中文化**
   这些兜底（否则与该设计自相矛盾，且源码里英文≠漏翻）。
   配套取舍：clap 会为每个含子命令的命令自动加一个 `help` 子命令，其描述是 clap 内建英文
   `Print this message or the help of the given subcommand(s)`（非 derive 兜底、无法用 `界面.取文`
   覆盖）。为守住「全树 `--help` 无英文泄漏」，`本地化clap()` 里对 root 及 install/lang/mapping/crate
   各调 `.disable_help_subcommand(true)` 移除内建 `help` 子命令——`rzc <命令> --help`/`-h` 仍全可用，
   仅失去 `rzc help <命令>` 这种冗余写法。**勿重新启用**，否则英文自动描述会重新出现在中文帮助里。这条红线现由常设门禁 `tools/zh-selfhost/help-check.sh`（`make gate` 的 zh-help-check）机器把守：自检负样本专门验证检测器非「永远绿」，再递归爬真实二进制整棵命令树复扫这两条。

**审计“全中文”不变式的方法**：要确认「自有符号已全中文化、无漏网英文」，不能拿
`grep -E 'fn [A-Za-z]'` 的一堆命中直接下结论——定义关键字同样大量出现在**字符串
夹具、注释、文档示例**里。本分支实测：`fn main`、`fn f`、`fn new`、`struct Window`、
`mod ascii` 等高频命中全部落在三类白名单内（① 代表要解析的**真实英文 Rust 输入**
的测试样本，如 `替换别名("fn f(x: &mut 字符串) {}")`、`"fn push(&mut self, …)"` 的
LSP JSON 夹具；② `//`/`///` 注释与文档示例；③ cargo/rustc ABI 强制的 `fn main` 入口）。
逐处回溯时：命中在 `"…"`/`r#"…"#` 串内或注释后 → 属白名单，留英文；行首真定义位
且非 `fn main` → 才是真违规候选。反向同样成立：把夹具串里的英文样本「顺手翻中」
会破坏断言（它们正是喂给别名替换/文档提取/LSP 翻译的英文输入）。故审「有没有漏」
与改「疑似漏」都得先做这层上下文归类。

**「本分支是不是已经没有英文了？」——标准答案**：不是，也不可能是；正确表述是
**「源真相的自有符号与注释散文已全中文，英文仅存于下述两层编译/门禁契约层」**（2026-10 全库实测：
符号层与注释/散文层漏网均为零）。本分支已按用户「中文专属」指令转为**仅内置 zh 语言包、无 VS Code 扩展**（他语产品资产与扩展已于 2026-10 三批提交整体剥离至 main），故不可动英文只剩两类，各自强行中文化的代价：

1. **结构必需**：eject 生成的 `.rs` 产物本就是标准英文 Rust（cargo/rustc 只认
   `fn main`、`use std::…`、serde/LSP 协议键）——这是自举设计的定义而非缺陷。
2. **门禁契约数据**：help-check 的英文负样本夹具、demo-check 的 `MUST_HAVE`
   预期改写串、clap 结构行（`Usage:`/`Print help`）——它们是「断言的靶心」，
   翻中即检测器失明（负样本不再是负样本）。

（旧第三类「产品多语内容」（`README.en/ja/ru/…`、`book/{en,ja,ru}`、`tutorials/{en,ja,ru}`、
`lang-packs/*`（非 zh）与 VS Code 扩展）已不再是本分支资产——它们属于 `main`。
本分支面向用户的产品文档与语言包均为中文单一。）

因此审「百分百中文」的正确姿势：先问该行英文落在哪层。落在上面两层=正确形态；
落在源真相的**定义位/注释散文**=真漏网（历史上每有发现当批翻转）。此结论另有
机器守门：help-check（用户面）、zh-verify（产物一致性）、doc-links-check（注释/文档
引用失效符号，cargo doc 权威判定）、覆盖面断言（英文孤儿 .rs）。

⚠️ **自动化的边界（勿 overtrust 门禁）**：`doc-links-check` 能零误判，是因为 `cargo doc` 有编译器作**权威预言机**（链接指向不存在的符号＝客观失效）。但「AI 直接在 `.zh` 代码定义位新写一个英文标识符」（如 `函数 calculate_sum(...)`）**没有这样的预言机**——它是合法 Rust、能 eject、`zh-verify` 字节一致、clippy 亦过，且「该不该翻中」取决于海量白名单（`use std`/`fn main`/serde·LSP 键/外部 crate 路径/测试夹具/std 方法透传…），硬做成门禁必然高噪声、基线易碎。故此类**不纳入机器门禁**，改由第一层**编写时规则**（`AGENTS.md`/`.qoder/rules` always-on 引导 + 术语表）与人工/AI 复核兜底；历史上发现即当批翻转。**结论**：`make gate` 全绿 ≠ 绝无英文——它保证的是「注释引用失效」「产物字节一致」「用户面本地化」「改写往返」这些**有预言机可客观判定**的维度；代码定义位的新英文标识符仍靠规则约束与评审（粗筛法：在 `.zh` 里搜不在字符串/注释内、又不落上述白名单的裸 ASCII 标识符作候选，逐个判该否翻中）。

## 4. 关键陷阱与技法（实证）

- **词条劫持**：裸标识符若恰等于某词条键（如 `代码`→code、`表`→Table），eject 会
  还原成英文破坏语法；局部名一律用**复合中文**（值项/键名项/偏移项…），选名前
  须排查是否落在任一 lang-pack 表（含第三方 crate 表的全局注入）。
- **改名脚本的行内分段**：按 code/字符串/注释三类段处理，字符串只同步
  `{变量}` 格式插值；`.` 前缀排除保护方法调用，但副作用是 `..e`、`..t.len()`
  范围运算符后的变量漏改——须 build 报错 + 全量复扫双保险兜底。
- **结构体字段简写**：`Foo { id, }` 改名前先显式化为 `id: id,`，否则左侧被
  冒号分界规则漏改。
- **同名复用**：不同闭包作用域允许同名中文参数（合法遮蔽）；同作用域必须碰撞核验
  （`(?<!\w)新名(?!\w)` 全文断言后再动手）。
- **CJK 密集文件批量改名走脚本**，编辑器多规则替换曾出现静默损坏（丢逗号、误改
  相邻标识符）；改完以 `git diff` 逐 hunk 核对。
- `json!`/`格式化!` 宏内 `"键": 变量` 的**裸值引用**按行过滤字符串键会漏检，
  交给编译 E0425 兜底。

## 5. 单文件翻转工作流（复用清单）

1. 勘查：列出该文件全部英文标识符/关键字位（分段扫描），区分改写面与保留面。
2. 定名：复合中文 + 词条表碰撞排查 + 同文件碰撞断言。
3. 替换：规则脚本（行段特例先于全局兜底）→ `regen.sh` → `cargo build --workspace --all-targets`。
4. 验收：`cargo fmt` → `cargo test --workspace` → `make gate`（产物逐字节一致）→ 提交。

## 6. 案例精读（改名前后真实对照）

以下四例均取自本分支终审批次的实战现场，每例展示「坑 → 修法 → 为什么」。

### 案例一：词条劫持——裸名恰等于词典键

```rust
// ✗ 字段名叫 代码：eject 时命中词条 "代码"=code，还原后结构体定义与使用错位
结构体 诊断码项 { 代码: 字符串, … }

// ✓ 复合中文名不落在任何词条键上，正反两向都稳定
结构体 诊断码项 { 诊断码: 字符串, … }
```

选名前必须把候选名到**全部** lang-pack 表（含第三方 crate 表，它会全局注入）
里查一遍；命中即换复合名（值项/键名项/偏移项…）。

### 案例二：点前缀盲区——`..e` 与 `.method` 共享排除规则

改名脚本用「前面是 `.` 就不改」保护方法调用，但范围运算符 `..e` 同样以点开头，
被一并保护漏改，而元组绑定 `(k, s, e)` 处已改——定义与使用割裂，编译 E0425：

```rust
// 绑定处已改，使用处漏改（..e 前的点触发排除）
让 (词元类别, 字面起点, 字面终点) = 跨度列表[j];
让 文字内容 = &源码内容[字面起点..e];   // ← 漏网，须行段兜底或手工修
```

教训：排除规则是双刃剑，每批改名后必须「build 报错 + 全量复扫」双保险。

### 案例三：冒号分界——参数位被字段保护规则误伤

「名字后跟 `:` 就当 JSON/结构体字段跳过」的规则，同样会挡住
「参数名: 类型」的定义位，函数体内使用处却已改：

```rust
// 修复前：定义位 method: &文本 被冒号规则保护未改，体内使用处已改 → E0425
函数 插入待处理(method: &文本) { … 如果 协议方法名 == "…" … }

// 修复后：参数位用类型白名单放行，定义/使用两侧咬合
函数 插入待处理(协议方法名: &文本) { … 如果 协议方法名 == "…" … }
```

### 案例四：字段简写——先显式化再改名

结构体字面量 `Foo { id, }` 的简写形态下，改名只动得了一侧：

```rust
// ✗ 直接改简写名：变量改了，字段名丢了（或反之）
待处理项 { id, … }

// ✓ 先展开成显式形式，字段名（英文契约）与变量名（中文）各自就位
待处理项 { id: 请求编号, … }
```

## 7. 文档自洽终审（失效引用交叉审读）

标识符/文件名中文化后，**文档（导航表、crate README、演示项目注释）里指向代码的
引用会滞后**——读者照着 `ui.rs`、`mapping_manager::MappingManager` 去翻，分支上
早就不存在这些英文名了。源码翻转收官后必须补一轮文档交叉审读。

做法是机械化扫描而非通读：从分支文档中抽出所有形如 `crates/**.rs|.zh|…` 的路径
与代码符号，逐个 `os.path.exists` / `grep 定义位` 验证是否仍指向分支真实存在之物；
命中即判「失效引用」还是「保留类」。本分支据此修过的高频类型：

| 失效点 | 修法 | 判据 |
|---|---|---|
| 导航/架构表里的旧英文文件名（`ui.rs`/`diagnostics.rs`/`response_map`/`translation_cache`） | 换成分支真实中文名（`本地化.rs`/`诊断处理.rs`/`响应映射`/`翻译缓存`） | 该文件在本分支已改名，路径失效 |
| README `rust,ignore` 用例里的英文 API 路径与类型名 | 对齐 `映射管理::映射管理器`、`源码转译(...)` 等真实符号；**顺带核对签名**——旧示例 `transpile_pipeline(..).output` 连返回形态都与分支不符 | 公开模块/函数随源码一并中文化 |
| 演示项目注释「真实后端 `module_path.rs`」等交叉引用 | 指回 `模块路径.zh` / `模块路径替换并映射` | 分支自有资产须自相咬合 |

**保留类（审读中判为不动，防误伤）**：`rust-analyzer`（被代理的外部工具专名）、
`module_paths.toml`/`ui.toml` 等 lang-pack **数据文件名**（属数据契约，分支上未改名、
真实存在）、`main.rs`/`build.rs`/`benches/hot_paths.rs`（cargo 对二进制入口、构建脚本、
bench 名的硬约定）、`RwLock`/`HashMap` 等 stdlib、CHANGELOG **历史条目**内的旧英文
文件名（记录当时产品线提交实况，改写历史即失真）、约定式提交格式示例里的 scope
占位。**面向终端用户的产品文档**（`tutorials/`、`book/`、`README.md`）在本分支已随中文
专属收敛为**单一中文**（他语版本已于 2026-10 三批提交剥离至 `main`，其语种在 `main` 上按
设计保持各语种、不做中文化）。但“不再有多语译本”不等于第五线审读跳过剩余中文文档——只要某文档
**内嵌/复刻了分支源码**或**指向具体编译器文件**，那些代码路径与符号引用仍须过第五线
扫描（例如中文母本教程第二十五章内嵌了 `.zh-demo/src/main.zh` 并自称“逐行对应”，
改名后就得同步其内嵌副本，否则声明被证伪）。区分：“不改写译本的语种”与“不修正失效
的源码指针”是两回事。

> 脚本化验收：`regen --check` 只保证 `.zh→.rs` 产物一致，看不见文档里的引用漂移；
> 文档失效引用须单独跑一遍「路径存在性 + 符号定义位」扫描，每轮改名批后重跑。

## 8. 体验本分支

```bash
git checkout exp/zh-selfhost
bash tools/zh-selfhost/regen.sh          # 从 .zh 重新生成全部 .rs
cargo test --workspace                   # 同一套测试全绿
make gate                                # 源真相与产物一致性门禁
```

想直观感受「中文方言写真实 Rust」，跑用户风格最小演示项目 `.zh-demo/`（不在

```bash
rzc run .zh-demo/src/main.zh             # 方言转译后编译并执行
make zh-demo-check                       # 改写往返校验（先 --self-test 自检检测器非永绿，
                                         # 再 eject 验产物命中预期英文改写且用户中文类型
                                         # 存活；已纳入 gate 链，并作为独立步进 CI test job
                                         # （用 --rzc target/debug/rzc 指向 CI 构建产物）
```

每个 `feat(zh-selfhost)` 提交的说明记录了当批改名映射与保留判据，
可按提交历史通读整个翻转过程。
