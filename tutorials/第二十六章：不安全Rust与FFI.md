# 第二十六章：不安全 Rust 与外部函数接口

## 26.0 学习目标

读完这一章，你将能够：

1. 解释"安全 Rust"到底在防什么，以及为什么必须有"不安全 Rust"；
2. 说出 `不安全` 块的**五种超能力**；
3. 创建、解引用**裸指针**，并说出它与引用的区别；
4. 用**封装原则**把不安全实现包进安全接口；
5. 用 `外部` 声明 C 语言函数（**外部函数接口**），在 Rust 里调用它；
6. 用 `#[repr(C)]` 控制结构体的内存布局，理解跨语言传递数据的规则。

> ⚠️ 这一章是**进阶内容**，可以留到最后再读。前二十五章里的所有代码都不需要用到本章知识。
> 记住本章开头这句话：**不安全代码不是"没有安全检查"，而是"编译器不帮你检查，你自己要负责"**。

## 26.1 为什么需要不安全代码

前面的章节里，我们反复强调 Rust 的安全性：借用检查器不让悬空引用、所有权保证每个值只有一个主人、数组越界直接恐慌……

这些保障是编译器**免费送给你**的——只要你的代码不含 `不安全` 块，编译器就会把好每一道关。

但现实世界有编译器管不到的角落：

- 操作系统和 C 库的函数（比如 `abs`、`printf`）没有所有权、没有借用检查；
- 有些数据结构在安全 Rust 里**实现不了**，只能靠手工管理内存；
- 硬件寄存器、共享内存等场景，必须直接读写内存地址。

于是 Rust 给了你一个"后门"：**`不安全` 块**。

📖 **不安全 Rust**：在 `不安全` 块里，你可以做安全 Rust 禁止的操作——但编译器不再替你检查，**一旦出错就是未定义行为**，可能崩溃、可能内存损坏、可能"碰巧正常工作"直到某天爆炸。

💡 **比喻**：安全 Rust 像在**游乐场**里玩——每个项目都有护栏和安全员。`不安全` 块像**走出游乐场大门**：自由了，但车来车往，撞上就是你的责任。

> 📖 **未定义行为**：程序做了语言规范没定义的操作，编译器"怎么处理都算对"。未定义行为是 Rust 里最危险的词——它可能不报错、不崩溃，而是悄悄把数据弄坏。

## 26.2 五种超能力

`不安全` 块里可以做**且只能做**这五件事（在块外做会编译报错）：

| # | 超能力 | 中文 | 例子 |
|---|--------|------|------|
| 1 | 解引用裸指针 | `*const 整数` 取 `*指针` | 读写原始内存地址 |
| 2 | 调用不安全函数 | 函数体里有 `不安全` 的 `外部` 函数 | 调 C 库、调操作系统接口 |
| 3 | 访问或修改可变静态变量 | `静态 可变 全局计数: 整数` | 全局计数器 |
| 4 | 实现不安全特征 | `不安全 特征` | 手写 `发送`/`同步` 特征 |
| 5 | 访问联合体字段 | `联合体` | 同一块内存多种解释 |

只要没在做这五件事，`不安全` 块里的其他代码和普通代码**一样安全**：

```rust
函数 主函数() {
    // 这里面的加法、打印都是普通安全操作
    不安全 {
        让 一 = 1;
        让 二 = 2;
        打印行!("{} + {} = {}", 一, 二, 一 + 二);
    }
}
```

输出：

```
1 + 2 = 3
```

本章重点讲第 1 种（裸指针）和第 2 种（外部函数），它们是教学与实操中使用最多的。

## 26.3 裸指针

之前学的引用（`&`、`&可变`）有三个铁律：非空、指向有效内存、借用检查器盯着生命周期。**裸指针**把这三条都扔了。

📖 **裸指针**：写法和 C 语言指针几乎一样的内存地址。两种：

- `*const 整数`——只读裸指针；
- `*可变 整数`——可写裸指针。

⚠️ 名字里带星号 `*`，但**不要解引用**（`*指针` 取值）——解引用裸指针是超能力第 1 种，必须在 `不安全` 块里。

裸指针和引用的区别：

| | 引用 `&` | 裸指针 `*const` |
|---|---|---|
| 是否可以为空 | 不可以 | **可以**（写 `std::ptr::null()`） |
| 是否自动管理 | 是（借用检查器） | 否（没人管） |
| 能否绕过借用规则 | 不能 | **能**（这就是危险所在） |
| 解引用要不要 `不安全` | 不用 | **要** |

### 把引用转成裸指针

裸指针最常用的来源：把一个安全引用 `作为` 成裸指针：

```rust
函数 主函数() {
    让 值 = 42;
    // &值 是普通引用，用 作为 把它转成裸指针——转换本身是安全的
    让 指针: *常量 整数 = &值 作为 *常量 整数;

    // 但"读指针指向的东西"是不安全的，必须包在 不安全 块里
    不安全 {
        打印行!("指针指向的值: {}", *指针);
    }
}
```

输出：

```
指针指向的值: 42
```

### 通过裸指针改写值

想要**可写**的裸指针，用 `*可变`，配合 `可变`：

```rust
函数 主函数() {
    让 可变 值 = 10;
    // &可变 值 是可变引用，转成可写裸指针
    让 指针: *可变 整数 = &可变 值 作为 *可变 整数;

    不安全 {
        *指针 = 20;      // 通过裸指针把值改成 20
    }
    打印行!("值现在是 {}", 值);
}
```

输出：

```
值现在是 20
```

注意 `值` 原本是 `让 可变` 声明的，所以既可以被引用借用，也可以被裸指针改写。如果你在 `不安全` 块外写 `*指针 = 20;`，编译器会直接拒绝。

## 26.4 封装原则：安全接口包住不安全实现

裸指针这么危险，难道每个用它的地方都要小心翼翼？不是——Rust 社区有个铁律：

> 📖 **封装原则**：把 `不安全` 代码**封装在安全函数内部**，调用者永远不需要写 `不安全`，也永远接触不到裸指针。

标准库里到处是这样的例子：`向量` 的底层就是一块裸指针管理的内存，但你在安全 Rust 里随便用 `向量`，因为 `向量` 内部把 `不安全` 全包好了。

我们写一个自己的例子：从切片里取第一个元素。切片非空时，首元素必然有效——这个"我们保证它安全"的推断，写在安全函数的注释里，调用者零负担：

```rust
// 安全接口：调用者不需要写 不安全
函数 求首元素(切片: &[整数]) -> 整数 {
    // 调用者保证切片非空（见练习），所以解引用首元素必然有效
    不安全 {
        *切片.作为指针()   // 作为指针 把切片转成裸指针，* 取出第一个元素
    }
}

函数 主函数() {
    让 数据 = [10, 20, 30];
    打印行!("首元素: {}", 求首元素(&数据));
}
```

输出：

```
首元素: 10
```

`*切片.作为指针()` 做了什么？`切片.作为指针()` 得到指向第一个元素的裸指针，`*` 解引用拷贝出 `10`。如果 `数据` 是空切片，这就是未定义行为——所以封装时**在注释里写清楚前置条件**（调用者要保证非空），这是不安全代码的标准做法。

## 26.5 外部函数接口：调用 C 语言函数

**外部函数接口**是"在 Rust 里调用其他语言（主要是 C）写的函数"的技术。操作系统、底层库（数据库、图形库、压缩库……）几乎都有 C 接口，外部函数接口是 Rust 和它们对话的桥梁。

### 声明外部函数

用 `外部` 关键字声明一段"外部代码"：**只有函数签名，没有函数体**，函数体在 C 那边：

```rust
// 声明 C 标准库的求绝对值函数
// "C" 表示使用 C 语言的调用约定
外部 "C" {
    函数 abs(数字: 整数) -> 整数;
}
```

- `外部` 对应 Rust 的 `extern` 关键字；
- `"C"` 是**调用约定**，告诉编译器"这是按 C 规则传递参数的函数"；
- 声明的函数和普通函数一样用 `函数` 关键字，但没有函数体，以分号结尾；
- ⚠️ **函数名必须用英文**：函数名要和 C 那边的真实符号名逐字一致（`abs` 就是 C 语言的真实符号名），Rust 禁止在 `外部` 块里用中文函数名（编译器报错"extern 块中不能使用非 ASCII 标识符"）。

### 调用外部函数

外部函数默认是**不安全的**（因为 Rust 不知道 C 那边会不会遵守规则），调用必须包在 `不安全` 块里：

```rust
外部 "C" {
    函数 abs(数字: 整数) -> 整数;
}

函数 主函数() {
    让 数字 = -42;
    让 结果 = 不安全 { abs(数字) };
    打印行!("绝对值({}) = {}", 数字, 结果);
}
```

输出：

```
绝对值(-42) = 42
```

> 💡 在 Unix（Linux/macOS）上，`abs` 来自 C 标准库 `libc`，Rust 默认会链接它，这段代码可以直接运行；在 Windows 上需要给 `外部` 块加 `#[link(name = "msvcrt")]` 指定链接库名。

### 为什么调用外部函数是"不安全的"？

因为 C 函数对 Rust 一无所知：

- C 可能返回一个野指针（指向已释放内存）；
- C 可能在你背后改写数据，破坏 Rust 的所有权规则；
- C 不检查你传的参数类型对不对（`整数` 之外的任何类型它都照单全收）。

所以**调用外部函数 = 自己背安全责任**，必须写 `不安全`，并且：

1. 确认签名和 C 那边的真实签名一致（类型、参数个数、返回值）；
2. 确认传进去的数据在函数执行期间有效；
3. 优先把外部函数**包进安全封装**（26.4 的封装原则），让业务代码远离 `不安全`。

## 26.6 repr(C)：内存布局对齐

用外部函数接口把结构体传给 C 函数时，还有个坑：**Rust 结构体在内存里怎么排字段，Rust 自己说了算**，而且默认会**重排字段**来省内存！

```rust
结构体 混合 {
    甲: 字节,     // 1 字节
    乙: 无符号整数, // 4 字节
    丙: 字节,     // 1 字节
}
```

在 Rust 默认布局下，编译器可能把 `乙` 挪到最前面，让结构体更紧凑。这在纯 Rust 内部没问题，但 C 那边**假设字段顺序固定**（C 结构体按声明顺序排）——两边对不上，数据就串了。

解法：给结构体加 `#[repr(C)]` 属性，强制按 C 的规则布局：

```rust
#[repr(C)]
结构体 混合布局 {
    甲: 字节,
    乙: 无符号整数,
    丙: 字节,
}

用 `标准库::内存::尺寸` 看看两种布局实际占多少字节：

```rust
结构体 混合 {
    甲: 字节,
    乙: 无符号整数,
    丙: 字节,
}

#[repr(C)]
结构体 混合布局 {
    甲: 字节,
    乙: 无符号整数,
    丙: 字节,
}

函数 主函数() {
    打印行!("默认布局: {} 字节", 标准库::内存::尺寸::<混合>());
    打印行!("紧凑布局: {} 字节", 标准库::内存::尺寸::<混合布局>());
}
```

输出：

```
默认布局: 8 字节
紧凑布局: 12 字节
```

- **默认布局 8 字节**：编译器把 4 字节的 `乙` 排最前，两个 1 字节的 `甲`/`丙` 排后面，加起来正好 8；
- **repr(C) 12 字节**：C 规则不允许重排，按 `甲(1) + 填充(3) + 乙(4) + 丙(1) + 填充(3)` 排，多了 4 字节填充。

多占内存是小事，**关键是两边字段顺序一致**。传给 C 的结构体、从 C 接收的结构体，一律加 `#[repr(C)]`。

## 26.7 常见错误

### 错误 1：在不安全块外解引用裸指针

```rust
函数 主函数() {
    让 值 = 1;
    让 指针 = &值 作为 *常量 整数;
    打印行!("{}", *指针);   // ❌ E0133：解引用裸指针需要 不安全 块
}
```

修复：把解引用包进 `不安全` 块：

```rust
函数 主函数() {
    让 值 = 1;
    让 指针 = &值 作为 *常量 整数;
    不安全 {
        打印行!("{}", *指针);   // ✅
    }
}
```

### 错误 2：裸指针解引用已释放的内存

```rust
函数 主函数() {
    让 指针;
    {
        让 数据 = 字符串::从("临时");
        指针 = 数据.作为指针();   // 数据离开作用域，内存被释放
    }
    不安全 {
        打印行!("{}", *指针);   // ❌ UB：悬空指针，行为未定义！
    }
}
```

这段代码**能编译，但它是错的**——`数据` 被释放后 `指针` 指向的内存已经不属于你了。真正的危险就在这里：**不安全代码的错误往往不报编译错，而是运行时悄悄出错**。

### 错误 3：外部函数签名写错

```rust
外部 "C" {
    函数 abs(数字: 长整数) -> 长整数;   // ❌ 声明是 64 位，C 那边其实是 32 位
}
```

C 的 `abs` 接收 `int`（32 位）。你把参数声明成 64 位，Rust 会按 64 位传参，C 按 32 位读取——参数直接错位。**签名必须和 C 的真实原型逐字节一致**，这是外部函数接口的头号事故源。

## 26.8 本章术语表

| 术语 | 解释 |
|------|------|
| 不安全块 | 允许做五种危险操作的代码块，编译器不再检查，责任自负 |
| 未定义行为 | 语言规范未定义的操作后果，可能不报错但悄悄弄坏数据 |
| 裸指针 | `*const T` / `*可变 T`，无安全检查的内存地址 |
| 封装原则 | 把不安全实现包进安全函数，调用者零负担 |
| 外部函数 | 用 C 调用约定声明的、没有函数体的外部函数 |
| 外部函数接口 | 调用其他语言（主要是 C）函数的接口技术 |
| 调用约定 | 函数参数/返回值如何传递的规则（"C" 是标准的一种） |
| repr(C) | 强制结构体按 C 规则布局的属性，跨语言传数据时使用 |
| 内存填充 | 字段之间为了对齐而空出的字节 |

## 26.10 常见问题

**问：写了 `不安全` 的代码就一定危险吗？**
答：不一定。`不安全` 只是把"编译器检查"换成"你保证正确"。如果封装得当（比如 `向量` 内部），用户可以完全感受不到 `不安全`。危险的不是关键字本身，而是**你在不安全块里做出的保证是否成立**。

**问：解引用裸指针，为什么有时安全有时不安全？**
答：解引用本身必须写在 `不安全` 块里（编译器要求）；但"这个指针指向的内存还有效吗"这个问题，编译器不回答，得你自己证明。你的证明成立，代码就安全；证明不成立，就是未定义行为。

**问：我需要用 `不安全` 做项目吗？**
答：绝大多数教学项目和业务代码**完全不需要**。标准库已经把 99% 的不安全细节包好了。你只需要：能读懂别人的 `不安全` 代码、知道何时绝不碰 `不安全`（比如写网页后端）、将来需要调 C 库时知道有外部函数接口这条路。

**问：Rust 有 `垃圾回收` 吗？为什么不安全代码会内存泄漏？**
答：Rust 没有垃圾回收，靠所有权自动释放。`不安全` 代码可以绕过所有权（比如把裸指针存起来），一旦绕过了，"谁负责释放、何时释放"就变成你的责任，忘了释放就泄漏。
