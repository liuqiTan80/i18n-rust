# 第十八章：包管理与构建

## 18.0 学习目标

读完这一章，你将能够：

1. 说出 **`Cargo.toml`** 的三大板块（身份、依赖、配置）；
2. 用命令给项目**添加第三方库**；
3. 分清 **调试构建**与 **发布构建**的用途；
4. 分清**可执行文件**与**库**；
5. 知道构建产物藏在哪个目录；
6. 看懂版本号的三段式（主.次.补丁）。

---

## 18.1 项目也要办身份证

一个项目就是一堆文件——编译器怎么知道：叫什么名字？用了哪些别人的库？怎么编译？

💡 **比喻**：项目像开一家公司，得先**办营业执照**。Rust 世界的营业执照叫 **`Cargo.toml`**，而发证机关叫 **Cargo**（rzc 内部就带着它干活）。

第二章我们用 `rzc init 我的项目` 造项目，它生成的文件是：

```
我的项目/
├── Cargo.toml     <- 营业执照
└── src/
    └── main.zh      <- 源代码
```

## 18.2 Cargo.toml 逐行读

`rzc init` 生成的真实内容：

```toml
[package]
name = "我的项目"
version = "0.1.0"
edition = "2024"

[dependencies]
```

| 字段 | 含义 |
|---|---|
| `[package]` | 身份信息板块 |
| `name` | 项目名（发布后别人靠它找你） |
| `version` | 版本号，三段式，见下文 |
| `edition` | Rust 版本纪元，决定语言规则，`2024` 是新版 |
| `[dependencies]` | 依赖清单——用到哪些第三方库，写在这里 |

📖 **依赖**：你项目引用的别人的库。写进清单后，构建时自动下载、编译、链接。

### 版本号三段式

`0.1.0` 读作"主版本.次版本.补丁版本"：

- **补丁**（第三位）：修缺陷，不改变用法；
- **次**（第二位）：加功能，老用法照旧；
- **主**（第一位）：大改，老用法可能失效。

约定：`0.` 开头的库还算年轻，随时可能变脸；`1.` 以上算成熟稳定。

## 18.3 添加第三方库

想用一个现成的库（比如序列化库 `serde`），两种办法：

### 办法一：命令行添加

```bash
cargo add serde
```

它自动在 `Cargo.toml` 里写上：

```toml
[dependencies]
serde = "1.0"
```

rzc 也提供同样的快捷命令（VS Code 扩展里也有"添加依赖"命令）：

```bash
rzc add serde
```

### 办法二：手写

直接编辑 `Cargo.toml`，把依赖抄进 `[dependencies]`。下次构建时自动下载。

> ⚠️ 下载依赖需要联网。公司内网、教室机房记得提前备好。

> 🔒 **新手第一道墙**：刚 `rzc init` 完就直接 `rzc add`，命令会在联网之前失败。
> rzc 认得这个原因，会把一句母语指引排在 Cargo 原文前面（下面是真实输出）：
>
> ```text
> 这个项目还没有 Cargo 能读取的构建入口：`Cargo.toml` 未声明 [lib]/[[bin]]，`src/` 下也没有 src/main.zh 对应的 .rs 文件。先运行 `rzc check src/main.zh` 生成标准 Rust 入口，再重试本命令
> error: failed to parse manifest at `问候器/Cargo.toml`
>
> Caused by:
>   no targets specified in the manifest
>   either src/lib.rs, src/main.rs, a [lib] section, or [[bin]] section must be present
> ```
>
> `Cargo.toml` 没写错。`rzc init` 生成的是 `src/main.zh`，而 Cargo 只认 `src/main.rs`——
> 那个文件要等 `rzc check` 或 `rzc run` 转译后才存在。**先 `rzc check src/main.zh` 一次，
> 再回来 `rzc add serde`。**（18.10 错误五是同一件事，包括 Cargo 直接把这堆英文丢给你的场合。）

## 18.4 构建：两种口味

### 日常开发：默认构建

```bash
cargo build
```

产物在 `target/debug/` 下。编译快、带调试信息，**适合写代码时反复跑**。`rzc run` 背后就是它。

### 发布上线：优化构建

```bash
cargo build --release
```

产物在 `target/release/` 下。编译器花时间做**优化**（跑得更快），编译本身慢一些。**给用户用的最终版本**一定用它。

💡 **比喻**：调试版是**试做版**——做得快，方便随时改；发布版是**精装版**——慢工出细活，拿来上架。

> ✨ `target/` 目录可以随便删——都是构建产物，删了重新编译就回来。所以 `.gitignore` 里总写着它。

## 18.5 可执行文件还是库？

一个项目可以产出两种东西，rzc 两种入口都认：

| 类型 | 入口文件 | 转译产物 | 能做什么 |
|---|---|---|---|
| 可执行文件 | `src/main.zh`（母语别名 `src/主函数.zh` 也行） | `src/main.rs` | `rzc run` / `rzc check` |
| 库 | `src/lib.zh` | `src/lib.rs` | 只能 `rzc check`（库里没有主程序，run 无从运行） |

这两个名字都是 Cargo 自己定死的发现规则，rzc 照搬，所以**造方言库不用配置任何东西**：
写 `src/lib.zh`，`rzc check` 就把标准 Rust 产物放到 `src/lib.rs`，Cargo 自动认出这个库
目标。下面是一段真实终端记录，`src/lib.zh` 的内容只有三行：

```text
公开 函数 问候() -> 整数 {
    42
}
```

```bash
rzc check src/lib.zh
```

```text
✅ 编译成功，没有错误。
```

```bash
cargo build
```

```text
   Compiling 问候库 v0.1.0 (/tmp/t185/问候库)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.05s
```

两条边界值得记住：

- **`lib` 没有母语别名。** `lib` 不是 Rust 关键字，各语言包都不翻译它，所以库入口只能
  叫 `src/lib.zh`——写成 `src/库.zh` 只是个普通模块。这与 `main` 不对称，是有意取舍：
  造库要的是零配置，不是文件名本地化。
- **`[lib]` 不用声明，但声明了也照办。** 如果你手上有老项目写着
  `[lib] path = ".rz/gen/src/lib.rs"`（在 rzc 认库入口之前那是唯一的造库配方），rzc 会
  按你的声明把产物写在托管目录里，不会另开一份 `src/lib.rs` 把两边搞成两个版本。

库不能 `run`——这不是限制，是事实：库没有可执行的主程序。

```bash
rzc run src/lib.zh
```

```text
错误：src/lib.zh 是库入口（产物是 Cargo 的 src/lib.rs）：库里没有可执行的主程序，
`rzc run` 运行不了它。校验代码用 `rzc check src/lib.zh`；要让程序跑起来，请另写一个
方言主程序入口来调用这个库，或用 `cargo test` 运行库里的测试
```

> ❌ 没有 `rzc init 名字 --lib` 这个参数，加了会被拒：`error: unexpected argument '--lib' found`。
> `rzc init` 永远给你可执行项目，库文件自己新建就行。

很多项目两个都要：库放逻辑，`main.zh` 当命令行门面。这种「一个包既是库又有程序」的布局
在 Rust 里很常见，但方言项目里它有三个坑，按顺序踩：

1. 库和主程序是**两个 crate**，`main.zh` 要用库里的东西得写 `使用 包名::翻倍;`——包名就是
   `Cargo.toml` 里 `name` 那个标识符，不是你写的文件名；
2. **先 check 库，再 check 主程序。** `rzc check src/main.zh` 会顺带转译 `src/lib.zh`，
   但产物落在托管目录，Cargo 认不到；库的 `src/lib.rs` 还没生成时，`使用 calc::翻倍;`
   会报 `错误[E0432]: 无法解析导入路径`。rustc 自己附的建议是「若要使用名为 calc 的第三方库，
   请运行 `cargo add calc`」——`calc` 是你自己的 crate，而 Cargo 不允许一个包依赖自己
   （实测 ``error: cannot add `calc` as a dependency to itself``），照着做只会白跑一趟。
   所以 rzc 把这条换成了能走通的动作：

   ``"calc" 是本项目的包名，不是第三方库——Cargo 不允许一个包依赖自己，`rzc add calc` 必然失败。要用本项目自己的库代码，先运行 `rzc check src/lib.zh` 生成 Cargo 的 src/lib.rs，然后重新校验``

   跑一次 `rzc check src/lib.zh`、再 check 一次主程序，`rzc run src/main.zh` 就正常打出 `42`；
3. **包名必须是 ASCII。** `name = "计算器"` 这种中文包名，只有库或只有主程序时都能编；
   一旦两者同时存在，Cargo 要用 `--extern` 把库传给主程序，立刻撞上 rustc 硬错
   ``crate name `计算器` passed to `--extern` is not a valid ASCII identifier``（这条消息
   目前没有母语译文，会原样显示）。

实际写方言代码时，**只想复用的逻辑通常直接写成模块文件**（`src/工具.zh`，由 `main.zh` 里
`mod 工具;` 引进去，第十七章），连库都不用建——上面三条坑也就都不存在了。

Cargo 最终读的永远是标准 Rust 产物，所以任何 Cargo 命令都得**先跑过一次 `rzc check`**（18.10 错误五）。

## 18.6 常用命令速查

| 命令 | 作用 |
|---|---|
| `rzc init 名字` | 新建中文项目 |
| `rzc run src/main.zh` | 编译并运行 |
| `rzc check src/main.zh` | 只检查不运行（快） |
| `cargo build` | 构建（调试版） |
| `cargo build --release` | 构建（优化版） |
| `cargo test` | 运行测试（第二十一章见） |
| `rzc add 库名` | 添加依赖，并告诉你这个库有没有母语别名 |
| `cargo add 库名` | 同上，但不报母语别名（Cargo 原样输出） |

## 18.7 完整示例：从零到发布

把本章流程完整走一遍（以真实终端为准）：

```bash
# 1. 办营业执照
rzc init 问候器
cd 问候器

# 2. 写代码（src/main.zh）
```

`src/main.zh`：

```rust
函数 主函数() {
    打印行!("你好，世界！");
}
```

```bash
# 3. 开发期：反复运行调试
rzc run src/main.zh

# 4. 只检查，不运行（更快）
rzc check src/main.zh

# 5. 发布：编译优化版
cargo build --release

# 6. 运行成品
./target/release/问候器
```

## 18.8 逐行解释

- **步骤 1**：`rzc init` 生成 `Cargo.toml` 和 `src/main.zh`，语言包已内置；
- **步骤 3**：`rzc run` = 转译 + 编译 + 运行一条龙，写完就跑。**顺带把 `src/main.rs` 生成了**，步骤 5 的 `cargo build` 因此才有的可读——先跑一次 `rzc check src/main.zh` 也等价；
- **步骤 4**：`check` 跳过生成可执行文件，只做类型检查——改代码后先检查，省时间；
- **步骤 5**：`--release` 触发优化编译，产物进 `target/release/`；
- **步骤 6**：直接执行成品，不经过任何工具链。

## 18.9 运行结果

步骤 1 的输出：

```
✅ 项目 '问候器' 创建成功！
   语言包已内置，无需手动复制。如需自定义，可创建 lang-packs/zh/ 目录覆盖。
   使用 `rzc run src/main.zh` 运行。
```

步骤 3 的输出：

```
你好，世界！
```

## 18.10 常见错误与解决

### 错误一：依赖下载失败

命令卡在 `Updating crates.io index`，然后报网络类错误。**解决**：检查网络；公司内网可配置镜像源（问管理员要地址写进 `~/.cargo/config.toml`）。这类错误由 Cargo 自己产出，**不随界面语言翻译**，原文就是排查线索，别当成 rzc 的错。

### 错误二：版本号写错

```text
    Updating crates.io index
error: the crate `serde@99.0` could not be found in registry index.
```

**解决**：去库的主页查最新版本号，或者干脆 `cargo add 库名`（不带版本）让它自动选最新。注意分隔符是 `@`：写成 `serde==99.0` 问的不是版本而是名字，Cargo 答 `error: invalid character `=` in package name`。

### 错误三：找不到可执行文件

`./target/release/主函数` 不存在？**解决**：可执行文件名 = `Cargo.toml` 里的 `name`（中文项目名可能已被净化成合法字符），去 `target/release/` 下 `ls` 看看真名。

### 错误四：改了 Cargo.toml 没生效

依赖改了但代码报"找不到库"。**解决**：重新构建一次，让 Cargo 重新解析依赖清单。

### 错误五：`no targets specified in the manifest`

方言项目里最响的一堵墙，`cargo build`、`cargo add` 等任何 Cargo 命令都可能撞上来：

```text
error: failed to parse manifest at `demo/Cargo.toml`

Caused by:
  no targets specified in the manifest
  either src/lib.rs, src/main.rs, a [lib] section, or [[bin]] section must be present
```

Cargo 从没听说过 `.zh` 文件，它要的是 `src/main.rs`，而那个文件只在 rzc 转译之后才存在。**解决**：`rzc check src/main.zh` 跑一次，产出标准 Rust 入口，再重复你的 Cargo 命令。

`rzc add` 会把这句母语指引排在 Cargo 原文之前（18.3 的陷阱框）；Cargo 本身不本地化，直接从 shell 敲 `cargo build` 看到的仍是上面那段英文——把 `Caused by` 下面两行读成「还没有 `.rs` 入口」，然后去跑 `rzc check`。

## 18.13 常见问题

**问：Cargo 和 rzc 是什么关系？**

答：rzc 是中文前门——把 `.zh` 转译成 Rust、把错误翻成中文；真正编译、下载依赖、管理构建的是背后的 Cargo 与 rustc。两者分工合作。

**问：`Cargo.lock` 是什么？**

答：依赖的"快照"——记录了这次构建用到的**每个库的确切版本**。团队共享它，保证所有人编译出的东西一模一样。

**问：依赖库也能是中文写的吗？**

答：依赖库本身用标准 Rust 写（`.rs`）。你的中文代码引用它们没问题——rzc 只转译你的 `.zh` 文件。

**问：为什么 `target/` 那么大？**

答：里面存着每次构建的中间产物和产物，多个构建口味各存一份。正常现象，几十上百兆都可能。定期 `cargo clean` 清空。

**问：发布给别人用，该发什么？**

答：可执行程序 → 发 `target/release/` 下的可执行文件（注意对方操作系统要对应）；代码库 → 发布到仓库（如 crates.io）或直接把源码给对方。

**问：`edition = "2024"` 能改旧吗？**

答：能，但没必要。新纪元规则更完善，本书所有代码都按它写。
