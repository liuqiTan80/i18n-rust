# 第二十章：测试

代码写完了，怎么知道它是对的？你可以运行看看——但如果代码有一万行呢？你不可能每次都手动检查。

**测试**就是让程序自己检查自己——你写好"正确答案"，每次修改代码后，程序自动对比"实际结果"和"正确答案"。

这一章你将学会：什么是测试、怎么写测试、怎么运行测试、测试失败时怎么找出问题。

---

## 20.1 为什么要测试

> **生活类比**：测试就像**考试后的对答案**。你做完题后，拿出标准答案一道道对——发现错了就改。测试就是给代码"对答案"。

先看一个真实的痛点。假设你写了一个加法函数：

```rust
函数 加(甲: 整数, 乙: 整数) -> 整数 {
    甲 + 乙
}
```

写完你运行了一次，`加(1, 2)` 输出 3，看起来没问题。可是——

- 如果传负数呢？`加(-1, 2)` 应该等于多少？
- 如果传 0 呢？`加(0, 0)` 呢？
- 如果后来你改了函数里的代码，会不会把原来对的地方改坏了？

**只靠"运行一次看看"远远不够。** 你不可能每次改完代码，都把几百种情况手动试一遍。而且人容易漏——今天记得检查负数，明天就忘了。

```
不测试：
  写代码 → 运行 → "看起来对" → 上线 → 💥 出错了！

测试：
  写代码 → 对答案（自动） → 全对 ✅ → 上线
```

**测试的好处：**

- **自动化**：一秒钟检查几百种情况，不用人盯着
- **防倒退**：改完代码跑一遍测试，改坏的地方立刻暴露
- **当文档**：测试代码写着"这个函数应该干什么"，别人一看就懂

> ✨ **小提示**：测试不是"写代码的最后一步"——写代码时同步写测试，就像写作业时顺手对答案，别等全写完再补。

## 20.2 写第一个测试

先看完整代码，再逐行解释：

```rust
函数 加(甲: 整数, 乙: 整数) -> 整数 {
    甲 + 乙
}

#[测试]
函数 测试加法() {
    断言相等!(加(2, 3), 5);
    断言相等!(加(0, 0), 0);
    断言相等!(加(-1, 1), 0);
}
```

逐行解释：

- 第 1-3 行：一个普通的加法函数——这是**被测试的代码**（正式代码）
- 第 5 行：**`#[测试]`** 标记——告诉编译器"下面的函数不是普通函数，是考试题目"
- 第 6 行：**`断言相等!(加(2, 3), 5)`** ——检查"`加(2, 3)` 的结果应该等于 5，如果不等就报错"
- 第 7-8 行：再检查两种特殊情况（都是 0、负数），防止函数"只在某个情况对"

### `#[测试]` 是什么？

你可能注意到 `#[测试]` 和之前的代码长得不一样。这是 Rust 的**属性**（attribute）——一种"贴在代码上的小标签"，用来给编译器额外说明。

> **生活类比**：属性就像**贴在试卷上的便利贴**。同样的试卷（函数），贴上"这是期中考试"的便利贴，老师（编译器）就知道该特殊对待它。

```
函数 测试加法() { ... }      ← 普通函数，随程序一起运行
#[测试]
函数 测试加法() { ... }      ← 贴了标签：只在测试时运行，不算正式功能
```

`#[测试]` 是 Rust 官方的测试标签——编译器看到它，就会把这个函数当"考试题"：单独运行、汇报通过还是失败。你不需要自己写"怎么运行测试"的代码，编译器全包了。

### `断言相等!` 是什么？

`断言相等!` 是**断言宏**（宏 = 简化写法的快捷工具，第五章讲过）。它的作用是：**检查两个值是否相等，不相等就当场报错**。

> **生活类比**：断言就是"对答案"——"我认为答案是 X，如果不是就告诉我错了"。

```
断言相等!(加(2, 3), 5)
            ↑       ↑
        实际结果   期望答案
```

**注意参数顺序**：左边写**实际结果**（函数算出来的），右边写**期望答案**（你认为对的）。如果两边不相等，报错信息会同时显示左右两个值，方便你对照"算出来的是多少、应该是多少"。

```
测试的执行过程：

运行测试
    │
    ├── 加(2, 3) = 5？   → 5 == 5 ✅ 通过
    ├── 加(0, 0) = 0？   → 0 == 0 ✅ 通过
    └── 加(-1, 1) = 0？  → 0 == 0 ✅ 通过

    全部通过！✅
```

### 测试函数有什么特别？

- 测试函数**不需要返回任何东西**——它只负责"检查"，检查不过就自动报告失败
- 每个测试函数**独立运行**——一个测试失败不影响其他测试
- `#[测试]` 标记的函数**不会被算进正式程序**——发布程序时它不会出现

> ⚠️ **重要**：测试函数的名字**必须以 `测试` 开头**吗？不强制——Rust 不检查名字，只看有没有 `#[测试]` 标签。但大家都习惯用"测试"开头的名字（如 `测试加法`），这样"成绩单"上一眼能看出是哪个测试。

## 20.3 运行测试

### 第一步：翻译你的中文代码

中文 Rust 的代码需要先翻译成标准 Rust（`rzc` 会自动完成）。在项目目录里运行：

```bash
rzc check 文件.zh
```

这个命令会把你的中文代码翻译成 `src/main.rs`（同时检查有没有语法错误）。

### 第二步：运行测试

```bash
cargo test
```

它会找到所有标记了 `#[测试]` 的函数，逐个运行，然后给你一张"成绩单"。

> ✨ **小提示**：如果提示找不到 `Cargo.toml`，说明你不在项目目录里——先用 `rzc init 项目名` 创建项目，再进入项目目录操作（第十七章讲过）。

### 阅读成绩单（全部通过时）

```
running 1 test          ← 找到 1 个测试
test 测试加法 ... ok      ← 测试"测试加法"通过了（ok = 通过）

test result: ok. 1 passed; 0 failed   ← 总结：1 个通过，0 个失败
```

（实际输出还有 `0 ignored; 0 measured; 0 filtered out; finished in 0.00s` 这些细节——`ignored` 是被忽略的测试、`filtered out` 是被过滤掉的测试，现在不用管它们，只要看 `passed` 和 `failed` 两个数。）

### 阅读成绩单（有测试失败时）

如果某个测试挂了，成绩单会明确告诉你**哪个测试挂了、为什么挂**：

```
running 1 test
test 测试加法 ... FAILED       ← 失败！

failures:

---- 测试加法 stdout ----
thread '测试加法' panicked at src/main.rs:6:5:
assertion `left == right` failed
  left: 4
 right: 5

failures:
    测试加法                ← 点名：是它挂了

test result: FAILED. 0 passed; 1 failed
```

逐段解释：

- `test 测试加法 ... FAILED`：哪个测试失败了
- `src/main.rs:6:5`：**出错的位置**——第 6 行第 5 个字符（行号帮你快速定位）
- `assertion `left == right` failed`：有一条"左右相等"的断言没成立
- `left: 4` / `right: 5`：**左边（实际结果）是 4，右边（期望答案）是 5**——原来 `加(2, 3)` 算出来是 4！

> ✨ **小提示**：测试失败不可怕——它是在帮你抓 bug。看到 FAILED 时，按三步骤排查：① 看"点名"找到是哪个测试；② 看行号找到哪一行断言；③ 对比 `left`（实际）和 `right`（期望），想清楚为什么算错了，改好再跑。

## 20.4 三个断言宏

测试的"检查"全靠断言宏。一共三个，别混：

| 宏 | 检查什么 | 什么时候用 |
|------|---------|----------|
| `断言!` | 一个条件是否为真 | "这件事应该是真的" |
| `断言相等!` | 两个值是否相等 | "结果应该等于答案" |
| `断言不等!` | 两个值是否不相等 | "这两个不该一样" |

### `断言!` —— 检查条件为真

```rust
#[测试]
函数 测试条件() {
    断言!(5 > 3);                    // 5 大于 3 应该是真的
    断言!("abc".包含("b"));          // "abc" 包含 "b" 应该是真的
}
```

`断言!` 只接收**一个**条件。条件为真就通过，为假就失败。

### `断言相等!` —— 检查两值相等

```rust
#[测试]
函数 测试相等() {
    断言相等!(2 + 2, 4);  // 2+2 应该等于 4
}
```

### `断言不等!` —— 检查两值不相等

```rust
#[测试]
函数 测试不等() {
    断言不等!("你好", "世界");  // "你好" 不等于 "世界"
}
```

> ⚠️ **最容易犯的错**：`断言相等!` 和 `断言!` 混着用。
>
> - 想检查"两个值相等" → 用 `断言相等!`，它会告诉你两边各是多少
> - 想检查"一个条件成立" → 用 `断言!`
>
> 写成 `断言!(加(2, 3) == 5)` 也能跑，但失败时只告诉你"这个条件不成立"，不告诉你两边各是多少，排查起来费劲。**能说清"哪边对不上"的，优先用 `断言相等!`。**

> ✨ **小提示**：`断言相等!` 要求两个值能互相比较（比如都是整数、都是字符串）。不同种类的东西比不了——比如"数字 5"和"文字 5"，`断言相等!(5, "5")` 会直接编译报错，因为数字和文字本来就不是一回事。

## 20.5 测试"应该失败"的情况

有时候你想测试"这个函数应该报错"——比如传入非法参数时，函数应该返回错误而不是崩溃。

回想第十五章讲的 `结果` 类型：一个函数可能成功（返回 `结果::成功(...)`）也可能失败（返回 `结果::错误(...)`）。

```rust
函数 安全除法(甲: 整数, 乙: 整数) -> 结果<整数, 字符串> {
    如果 乙 == 0 {
        结果::错误("除数不能为零".转字符串())
    } 否则 {
        结果::成功(甲 / 乙)
    }
}

#[测试]
函数 测试除以零() {
    让 除法结果 = 安全除法(10, 0);
    断言!(除法结果.是否为错误());  // 除以零应该返回错误
}

#[测试]
函数 测试正常除法() {
    让 除法结果 = 安全除法(10, 2);
    断言相等!(除法结果.解包(), 5);  // 10 ÷ 2 = 5
}
```

逐行解释：

- 第 1-7 行：`安全除法` 函数——除数是 0 就返回 `结果::错误`（错误信息），否则返回 `结果::成功`（商）
- 第 9-13 行：**第一个测试——"除以零应该返回错误"**
  - 第 11 行：调用 `安全除法(10, 0)`，把结果存进变量 `除法结果`
  - 第 12 行：`除法结果.是否为错误()` 检查"结果是不是错误"——是错误就通过，不是就失败
- 第 15-19 行：**第二个测试——"正常除法"**
  - 第 17 行：调用 `安全除法(10, 2)`（正常情况）
  - 第 18 行：`.解包()` 从成功结果中取出值（10 ÷ 2 = 5），断言它等于 5

> ⚠️ **注意**：`解包()` 有风险——如果结果是错误，`解包()` 会让程序崩溃。所以只在"确定是成功"时才用它。测试里要检查"错误的情况"，用 `是否为错误()` 而不是 `解包()`。

```
两个测试各管一件事：

测试除以零：安全除法(10, 0) → 错误 ✅（测试"出错时应该出错"）
测试正常除法：安全除法(10, 2) → 5 ✅（测试"正常时应该正常"）
```

> ✨ **小提示**：好的测试不只测"正常情况"，更要测"边界和异常情况"——除数为 0、空列表、负数字……这些正是 bug 最爱藏的地方。

## 20.6 测试组织

> **生活类比**：测试代码和正式代码应该分开——就像"考试卷"和"课本"分开。测试代码只在"考试"（运行测试）时才用，不会出现在最终发布的程序里。

### 内联测试：`模块 测试`

小项目里，最常见的做法是在同一个文件里，把测试集中放进一个叫 `测试` 的模块：

```rust
函数 加(甲: 整数, 乙: 整数) -> 整数 {
    甲 + 乙
}

函数 减(甲: 整数, 乙: 整数) -> 整数 {
    甲 - 乙
}

// 测试模块——只在运行测试时编译
#[配置(测试)]
模块 测试 {
    使用 超级::*;  // 引入上面所有函数

    #[测试]
    函数 测试加() {
        断言相等!(加(1, 2), 3);
    }

    #[测试]
    函数 测试减() {
        断言相等!(减(5, 3), 2);
    }
}
```

逐行解释：

- 第 11 行：**`#[配置(测试)]`** ——"只在运行测试时才编译这个模块"。平时编译正式程序时，整个 `测试` 模块会被直接跳过，不占任何空间
- 第 12 行：**`模块 测试 { ... }`** 把所有测试放在一个"抽屉"里，和正式代码分开
- 第 13 行：**`使用 超级::*;`** ——`超级` 指"上一层的模块"（这里是文件最外层），`*` 表示"里面所有的东西"。整行的意思是："把外面定义的函数全部引入进来用"。没有这行，`测试` 模块里就看不到 `加`、`减`
- 第 16、22 行：每个测试函数仍然要单独加 `#[测试]` 标签——`模块 测试` 只是"装测试的抽屉"，抽屉里的每个函数还是要贴标签才算测试

```
代码结构：

src/main.zh
├── 正式代码
│   ├── 加()
│   └── 减()
│
└── 测试模块（只在测试时编译）
    ├── 测试加()
    └── 测试减()
```

> ⚠️ **为什么模块名要叫"测试"？** 不是必须——你可以叫任何名字。但 `测试` 是 Rust 社区约定俗成的名字，编译器也认识（`cargo test` 会自动寻找 `测试` 模块）。跟着惯例走，别人看你的代码也容易懂。

### 集成测试：`tests/` 目录

内联测试（`模块 测试`）测的是"单个函数对不对"。但有时候你想测试**整个项目配合起来**的样子——几个模块一起工作、数据从 A 流到 B。这时用 **`tests/` 目录**。

```
项目/
├── src/
│   ├── main.zh      ← 程序入口
│   └── lib.zh       ← 库入口（写"公开"的函数，供外面使用）
└── tests/
    └── 集成测试.zh  ← 独立测试程序
```

`tests/` 里的每个文件是一个**独立的测试程序**——它把项目当成一个"工具箱"来用：打开工具箱（`使用`），拿出工具（函数），测试它们好不好用。

集成测试文件里，用 `使用 项目名::函数名;` 把正式代码"借"进来：

```rust
// 文件：tests/集成测试.zh
使用 我的项目::加;

#[测试]
函数 测试加() {
    断言相等!(加(2, 3), 5);
}
```

逐行解释：

- 第 2 行：**`使用 我的项目::加;`** ——把项目 `我的项目` 里定义的 `加` 函数引入过来。**`我的项目` 必须和 Cargo.toml 里写的项目名一模一样**（第十七章讲过：`name = "我的项目"`）
- 第 3 行：这要求 `加` 在定义时标了 **`公开`**（第十六章讲过：不加 `公开`，外面的代码看不到它）：

```rust
// src/lib.zh 里：
公开 函数 加(甲: 整数, 乙: 整数) -> 整数 {
    甲 + 乙
}
```

- 第 5-7 行：和普通测试一样写断言

> ✨ **小提示**：小项目用"内联测试"（`模块 测试`）就够了；等你的项目有好几个文件、需要测试"几个功能配合起来对不对"时，再用 `tests/` 目录。两种方式可以同时用。

## 常见错误

### 1. 测试函数忘记标记

```rust
// ❌ 忘记加 #[测试]
函数 测试加法() {
    断言相等!(2 + 2, 4);
}

// ✅ 修复：加上 #[测试]
#[测试]
函数 测试加法() {
    断言相等!(2 + 2, 4);
}
```

**后果**：没贴标签的函数不是测试——`cargo test` 不会运行它，你的检查等于白写，而且编译器不会提醒你。

### 2. 断言写反了（实际值 vs 期望值）

```rust
#[测试]
函数 测试() {
    // ❌ 把期望答案写在左边，实际结果写在右边
    断言相等!(5, 加(2, 3));

    // ✅ 左边写实际结果，右边写期望答案
    断言相等!(加(2, 3), 5);
}
```

**后果**：`断言相等!` 本身不挑顺序（两边相等就过），但失败时输出的 `left` 和 `right` 会颠倒——你看到"left: 5, right: 8"会以为是函数算出了 5，其实是期望值。养成习惯：**左边实际、右边期望**。

### 3. 测试里用了"不确定"的值

```rust
// ❌ 坏例子：测试里依赖"不确定"的值（比如随机数、当前时间、网络请求）
// 函数 测试随机() {
//     让 数字 = 生成随机数();  // 结果每次不同
//     断言相等!(数字, 3);      // 有时过，有时挂
// }

// ✅ 好测试：只检查"确定的事"
#[测试]
函数 测试确定() {
    断言相等!(2 + 2, 4);     // 永远成立
}
```

**后果**：测试结果时好时坏——这次过、下次挂，你根本分不清是代码坏了还是运气不好。

> ✨ **小提示**：好的测试像"考试题"——**答案必须是确定的**。如果测试里用了随机数、当前时间、网络请求这些"每次都不一样"的东西，测试结果就不可靠了。真需要测这些时，先把"不确定"的部分接进来再测（高级技巧，这里先记住原则）。

### 4. 测试和正式函数重名

```rust
函数 加(甲: 整数, 乙: 整数) -> 整数 { 甲 + 乙 }

#[配置(测试)]
模块 测试 {
    使用 超级::*;

    #[测试]
    函数 加() {   // ❌ 和外面的 加 重名
        断言相等!(加(1, 2), 3);
    }
}
```

**后果**：模块里的 `加` 把外面引入的 `加` 遮住了，测试里调用的其实是"自己"——无限递归，程序崩溃。

**修复**：测试函数名字加上"测试"前缀（`测试加`、`测试加法`），既避免重名，又容易认。

## 本章小结

| 概念 | 一句话 |
|------|--------|
| 测试 | 对答案——让程序自己检查自己 |
| `#[测试]` | 属性（标签）——标记"这是考试题目" |
| `断言!` | 检查一个条件是否为真 |
| `断言相等!` | 检查两个值是否相等（左边实际、右边期望） |
| `断言不等!` | 检查两个值是否不相等 |
| `是否为错误` | 检查结果是不是错误（测"应该失败"的情况） |
| `解包` | 取出成功结果的值（只在确定成功时用） |
| `cargo test` | 运行所有测试 |
| `#[配置(测试)]` | 只在测试时编译的模块 |
| `模块 测试` | 装内联测试的"抽屉" |
| `使用 超级::*` | 测试模块里引入外面的函数 |
| `使用 项目名::函数` | 集成测试引入正式代码（项目名要与 Cargo.toml 一致） |

**下一章**：你将学习**闭包与迭代器**——更灵活地处理数据和函数。
