# 第二十章：并发与多线程

## 20.0 学习目标

读完这一章，你将能够：

1. 用**多灶台厨房**比喻解释线程；
2. 用 **`线程::生成`** 开新线程、用 **`等待线程`** 收尾；
3. 理解 **`移动`** 闭包为什么要把数据搬进线程；
4. 用**通道**在线程间安全传话；
5. 用 **`Arc` + `互斥锁`** 共享一份可修改的数据；
6. 记住并发铁律："**共享 + 可变**必须上锁或走通道"。

## 20.1 一个灶台不够快

一个程序默认从头到尾一条线执行——**一个灶台炒菜**，后面的菜全排队。

💡 **比喻**：饭店高峰期，一个灶台忙不过来。**线程**就是多开几个灶台，同时炒几道菜。

📖 **线程（thread）**：程序里一条独立执行的指令流。操作系统让它们在多个 CPU 核心上真正同时跑。

并发写错会出大事（两个厨师同时往锅里放盐）。别怕——**Rust 编译器就是你的后厨主管**，谁没按规矩来，编译阶段就拦下。

## 20.2 生成线程

```rust
使用 标准库::线程;

让 句柄 = 线程::生成(|| {
    打印行!("子线程：开工！");
});
句柄.等待线程().解包();
```

- **`线程::生成(|| { ... })`**：开一个新灶台，把闭包里的代码交给它做（闭包是什么？第二十二章细讲，这里当作"打包好的一段活"）；
- **`句柄`**：生成后拿到的"取餐号"，靠它跟踪这个线程；
- **`等待线程()`**：主线程停下来，等它干完再继续（= join）。不等的话，主程序可能先结束，子线程的活白干。

## 20.3 让线程歇一会儿

```rust
使用 标准库::时间::持续时间;

线程休眠(持续时间::从毫秒(50));
```

（需先 `使用 标准库::线程::线程休眠;` 引入。）模拟"干活要花时间"，演示顺序时有用。

## 20.4 通道：线程间传话的对讲机

多个线程之间怎么交流？**不许随便碰同一块数据**——用**通道**传消息：

💡 **比喻**：对讲机——一头说，另一头听。说完的话**所有权交给对方**，说话人就不能再改口了。

```rust
使用 标准库::同步::mpsc;

让 (发话口, 听话口) = mpsc::通道();

发话口.发送(字符串::从("任务完成，共 42 件")).解包();
让 收到 = 听话口.接收().解包();
```

- `通道()` 一次造出**一对**：发话口（发送端）+ 听话口（接收端）；
- `发送` 把数据**移进**通道——发完你就没份了（所有权转移！）；
- `接收` 会**阻塞等待**：没消息就一直等，有消息立刻拿。这保证"收到的一定是已发出的"。

> ⚠️ 发话口可以克隆出多份（多人对一人说），听话口只有一份——所以叫"多生产者，单消费者"（mpsc）。

## 20.5 共享数据：`Arc` + `互斥锁`

确实需要多人改同一份数据时（比如统计总数），两件套上阵：

```rust
使用 标准库::sync::Arc 作为 Arc别名;
使用 标准库::sync::Mutex 作为 锁别名;

让 计数器 = Arc别名::新建(锁别名::新建(0));
```

📖 **互斥锁（Mutex）**：公共厕所的门锁——**进去先锁门**，出来自动开。拿到锁（`加锁()`）才能读写数据，别人只能等。

📖 **原子引用计数（Arc）**：第十九章 `Rc` 的线程安全版。多线程共享钥匙必须用它（`Rc` 的记账不够稳，编译器拒绝它进线程）。

💡 **记忆口诀**：**Arc 管"几个人有钥匙"，锁管"一次只能进一人"。**

## 20.6 完整示例：工作间汇报

子线程干活、用通道汇报，主线程收报告——本章主菜：

```rust
使用 标准库::线程;
使用 标准库::线程::线程休眠;
使用 标准库::时间::持续时间;
使用 标准库::同步::mpsc;

函数 主函数() {
    // —— 生成子线程 ——
    让 句柄 = 线程::生成(|| {
        打印行!("子线程：开工！");
        线程休眠(持续时间::从毫秒(50));
        打印行!("子线程：收工！");
    });

    // —— 通道：线程间传话 ——
    让 (发话口, 听话口) = mpsc::通道();
    发话口.发送(字符串::从("任务完成，共 42 件")).解包();

    // 主线程先等消息，再等线程收尾
    让 收到 = 听话口.接收().解包();
    打印行!("主线程收到：{}", 收到);

    句柄.等待线程().解包();
    打印行!("主线程：全员收工");
}
```

## 20.7 逐行解释

- **第 1–4 行**：四件工具引入——线程、休眠函数、时长类型、通道模块。
- **第 7–11 行**：`线程::生成` 开出子线程：打印开工 → 睡 50 毫秒（模拟干活）→ 打印收工。
- **第 14–15 行**：造通道的一对端口，立刻发一条汇报消息。`发送` 把字符串移进通道。
- **第 18–19 行**：`接收` 等到消息（这里是秒到）后打印。
- **第 21 行**：`等待线程` 确保子线程的"收工"打印完成后，主线程才说"全员收工"。

## 20.8 运行结果

```
主线程收到：任务完成，共 42 件
子线程：开工！
子线程：收工！
主线程：全员收工
```

有意思的顺序：主线程**没等**子线程就收到了消息（通道独立于线程），但最后一句"全员收工"**一定**在最后——`等待线程` 兜住了底。

## 20.9 进阶示例：Arc + 锁的计数器

```rust
使用 标准库::线程;
使用 标准库::sync::Arc 作为 Arc别名;
使用 标准库::sync::Mutex 作为 锁别名;

函数 主函数() {
    让 计数器 = Arc别名::新建(锁别名::新建(0));
    让 副本 = 计数器.克隆();
    让 句柄 = 线程::生成(移动 || {
        让 可变 守卫 = 副本.加锁().解包();
        *守卫 = *守卫 + 1;
    });
    句柄.等待线程().解包();
    打印行!("计数：{}", *计数器.加锁().解包());
}
```

输出：`计数：1`

要点：

- `副本 = 计数器.克隆()`——给子线程一把钥匙（Arc 克隆便宜）；
- `移动 ||`——把 `副本` **搬进**闭包，线程才能拥有它（下一节讲）；
- `加锁()` 得到 `守卫`——守卫活着期间门锁着，`*守卫` 读写数据；守卫离开作用域自动开锁；
- 主线程打印也要先 `加锁`——锁内数据不能直接 `{}` 打印。

## 20.10 `移动` 闭包：把行李带进线程

子线程可能比主函数活得久。如果闭包只是"借"了外面的变量，线程跑到一半主人没了怎么办？

Rust 的规矩简单粗暴：**`移动`**（move）——把数据的所有权整个搬进闭包：

```rust
让 副本 = 计数器.克隆();
线程::生成(移动 || {
    // 副本 现在是线程自己的了
});
// 这里不能再碰 副本（但 计数器 本人还在）
```

所以正确姿势是：**先克隆（或多造几份），再移动**——每人一份，谁也不欠谁。

## 20.11 常见错误与解决

### 错误一：E0382 值在移动后被使用

线程生成时没克隆就 `移动`，之后还想用原值。**解决**：先 `克隆()`（或另造一份）再进线程。

### 错误二：把 `Rc` 传进线程

```
错误：`Rc` 不能在线程间安全传送
```

**解决**：换 `Arc`（原子版）。

### 错误三：忘 `等待线程`，输出残缺

子线程没打印完程序就退出了。**解决**：收尾前逐个 `句柄.等待线程()`。

### 错误四：锁着数据直接打印/比较

Mutex 里的值要先 `加锁()` 再 `*守卫` 取用。**解决**：一切操作都放进拿到守卫之后。

### 错误五：忘记引入工具

`线程`、`线程休眠`、`持续时间`、`mpsc` 都要 `使用` 引入。报错找不到名字时，先查 20.6 开头的四行。

## 20.12 本章术语表

| 术语 | 一句话解释 |
|---|---|
| 线程 | 一条独立执行的指令流 |
| 生成 | 开新线程，`线程::生成(闭包)` |
| 句柄 | 指向已生成线程的取餐号 |
| 等待线程 | 阻塞等待线程干完（join） |
| 通道 | 线程间传消息的对讲机（mpsc） |
| 发送/接收 | 通道的两端动作，接收会阻塞等待 |
| 移动闭包 | 把数据所有权搬进闭包的写法 |
| 互斥锁 | 一次只许一个线程读写的数据门锁 |
| 守卫 | 拿着锁的凭证，活着就锁着，走了自动开 |
| 原子引用计数 | 线程安全版的共享钥匙（Arc） |

> 📖 **提醒**：遇到不懂的词，随时回查全书开头的《总术语表》。

## 20.14 常见问题（FAQ）

**问：开越多线程越快吗？**

答：不是。线程数超过 CPU 核心数就变成"换班跑"，反而浪费。而且线程创建本身也有开销。经验：CPU 有几核就大致开几条，或者用线程池（库来管）。

**问：为什么 Rust 的并发"以难著称"？**

答：难在**编译期就拒绝数据竞争**——别的语言把这类 bug 留到运行时撞大运。写的时候多挨几下编译器教育，换的是上线后半夜不被叫醒。

**问：通道和锁怎么选？**

答：数据像"接力棒"一样在线程间传递 → 通道；多个线程要**就地修改同一份状态** → 锁。有句行话："别用共享内存来通信，用通信来共享内存"——优先通道。

**问：`解包()` 在并发代码里到处出现，不会出事吗？**

答：本章为简洁用了 `解包`。生产代码里：`等待线程` 失败说明线程恐慌了，`接收` 失败说明发送端全没了——都该用 `匹配` 认真处理。

**问：线程里能用第九章的字符串吗？**

答：能，`字符串` 可以安全移动进线程（它实现了传送特征）。`移动` 闭包带它进去完全没问题——这正是示例里通道发送字符串能成功的原因。

**问：异步（async）和线程是一回事吗？**

答：不是一回事。线程是操作系统级的并行；异步是一个线程内"等活儿时先干别的"的调度技巧。第二十四章《异步编程》详讲。
